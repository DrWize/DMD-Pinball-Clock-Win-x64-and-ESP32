# Reproducible current playback comparison

Run everything from the repository root in PowerShell. No ChatGPT, cloud service,
or GitHub query is required. This runner measures the current native Windows
renderer and both physical ESP32 clocks. It does not change playback speed,
scheduling, saved settings, Wi-Fi credentials, NTP, system clocks, or scene files.
The earlier 200-scene dataset under `output/esp32/sd-timing-20261016` is retained.

## Prerequisites

- Windows with PowerShell, .NET 10 SDK, and the complete source checkout and scenes.
  The first build may need to restore NuGet packages.
- ESP-IDF 5.5.2 and its Python environment with pyserial for firmware deployment.
  The PowerShell entry point selects the pinned IDF Python automatically; use
  `-Python C:\path\python.exe` if your installation differs. Python needs pyserial
  for device actions; report generation uses the standard library only.
- Both cards mounted in their clocks, containing the matching SCN library.
- Close serial monitors. The current setup is Waveshare 7 on COM4 and Waveshare
  3.49B on COM3. Device board, MAC, firmware and ELF hash are verified; port numbers
  alone do not establish identity.
- Keep the desktop unlocked and the visible Windows candidate unobscured during
  measurement. The runner temporarily prevents sleep and releases that request
  when it exits normally. Avoid other heavy workloads during a comparison.

Firmware must support `DMDTIMING:` protocol 1. The earlier
`1.9.0-serial-wifi.3` firmware supports provisioning but cannot capture timing.
Build and application-flash the timing candidate once:

```powershell
.\scripts\esp32\dev\Build-DmdClock.ps1 -Board Waveshare7 -Version 1.9.0-timing.2 -BuildDir build-current-timing-7
.\scripts\esp32\dev\Invoke-Idf.ps1 -ProjectPath .\firmware\dmdclock-esp32 -IdfArguments @('-B', 'build-current-timing-7', '-p', 'COM4', 'app-flash')
.\scripts\esp32\dev\Build-DmdClock.ps1 -Board Waveshare349B -Version 1.9.0-timing.2 -BuildDir build-current-timing-349b
.\scripts\esp32\dev\Invoke-Idf.ps1 -ProjectPath .\firmware\dmdclock-esp32 -IdfArguments @('-B', 'build-current-timing-349b', '-p', 'COM3', 'app-flash')
```

Application flashing retains NVS Wi-Fi settings and card contents. Capture is off
after boot and until a session explicitly enables it. `/api/state` exposes timing
protocol, enabled/active state and captured steps. No automatic flashing, reset,
or provisioning occurs in the comparison runner.

## Choose and freeze a test set

Start the interactive menu with no arguments:

```powershell
.\scripts\Compare-CurrentPlayback.ps1
```

Or prepare explicitly:

```powershell
.\scripts\Compare-CurrentPlayback.ps1 -Action Prepare -Output output/timing/reference-run -TestSet Standard50
.\scripts\Compare-CurrentPlayback.ps1 -Action Prepare -Output output/timing/five-percent -TestSet '5%'
.\scripts\Compare-CurrentPlayback.ps1 -Action Prepare -Output output/timing/ten-percent -TestSet '10%'
.\scripts\Compare-CurrentPlayback.ps1 -Action Prepare -Output output/timing/half-library -TestSet '50%'
.\scripts\Compare-CurrentPlayback.ps1 -Action Prepare -Output output/timing/custom-count -TestSet Custom -Size 75
.\scripts\Compare-CurrentPlayback.ps1 -Action Prepare -Output output/timing/custom-percent -TestSet Custom -Size '12.5%'
```

Prepare hashes the local SCNs and both live SD libraries, records their alignment,
and samples only the verified intersection. Percentages round up. With 2,416
matching files, the presets select 121, 242 and 1,208 scenes; 12.5% selects 302.
Counts must be positive integers no greater than the matching library; percentages
must be greater than zero and at most 100. Test size never changes the timing
thresholds. Use `-Port7 COM4 -Port349B COM3` to override ports.

The permanent `tests/fixtures/playback/Standard50-v1.json` freezes 20 previously
differing scenes, 20 diverse scenes and 10 matching controls, including hashes,
file timings, categories and execution order. Its provenance records the earlier
200-scene evidence. It is never regenerated by the runner. Missing or changed
reference files fail preparation. All sizes use the frozen reference order first;
larger sizes append a deterministic SHA-256 ordering using `-Seed` (default 50).
Changing seed affects only the additional scenes. Smaller sizes take a prefix.

Each preparation freezes `manifest.json`, `run.json`, live inventories,
`alignment.json`, firmware identities, and isolated Windows source and binaries.
The default reference and explicitly imported manifest are copied byte-for-byte.
Use a new directory for another version, importing the earlier manifest:

```powershell
.\scripts\Compare-CurrentPlayback.ps1 -Action Prepare -Output output/timing/next-version -Manifest output/timing/reference-run/manifest.json
```

This retains exact scenes, order and manifest hash while building the new Windows
candidate and recording the new firmware identities. Do not edit an existing run
or its frozen files to compare another build.

## Run, resume, report and clean up

```powershell
.\scripts\Compare-CurrentPlayback.ps1 -Action Run -Output output/timing/reference-run
.\scripts\Compare-CurrentPlayback.ps1 -Action Resume -Output output/timing/reference-run
.\scripts\Compare-CurrentPlayback.ps1 -Action Report -Output output/timing/reference-run
.\scripts\Compare-CurrentPlayback.ps1 -Action Cleanup -Output output/timing/reference-run
```

Run and Resume use identical frozen inputs. They verify selected local/card files,
Windows source/binaries and firmware build identities before capture. A different
build requires Prepare in a new directory. If Windows assigns different COM
numbers after reconnecting, pass the new ports to Resume or Cleanup; identities
must still match. Only one controller can own a run directory.

The first up to five scenes qualify capture overhead: three summary-only and
three detailed observations per scene and target (90 observations for five).
Detailed recording must not add both 5% and 50 ms in two of three paired runs.
A failed qualification blocks the main run and remains explicit in reports.
It estimates additional per-step recording overhead, not all instrumentation cost.

The main run records each scene three times on each target: nine measurements
per scene, 450 for Standard50. The three targets run concurrently; scenes within
each target follow the frozen order. A visible, isolated Windows process uses
separate settings and a loopback-only diagnostic API on port 17898. Do not launch
another comparison candidate on that port.

Press Ctrl+C once to request a stop after active captures finish and evidence is
saved. Resume validates existing host logs and retrieves committed device logs
before replaying missing cases. Corrupt evidence fails validation explicitly;
it is not silently accepted or replaced. Partial captures and uncommitted SD
files are never counted. A disconnected device needs its connection restored
before Resume/Cleanup can complete. No reconnect operation resets the device.

Sessions restore runtime display state on normal exit. Cleanup explicitly disables
the matching session. An idle orphan session expires after 180 seconds; reboot
also disables capture. Reports require confirmed cleanup on both clocks before
declaring completion. Raw logs remain available for later audits.

## Settings and interpretation

Temporary runtime settings are Basic orange, 100% brightness, no information
overlay or seconds, ESP32 glow 50%, and Windows 1x with normal glow enabled.
Windows currently offers an on/off glow control rather than a percentage; this
difference is recorded in run configuration and reports. Production rendering
code and saved settings are preserved.

ESP32 records loading, command, playback start/completion, every frame/step,
decode completion and rendering submission timestamps in RAM. It writes dedicated
JSONL logs under `/dmd/logs/comparison/<session>/<stage>/` only after playback.
Transfers verify exact byte count and SHA-256. Selected scene bytes are hashed
before and after playback. Loading, logging and transfer are outside playback
duration. Windows records observed animation steps and rendering submissions.

A duration difference is confirmed only when both 5% and 50 ms are exceeded in
the same direction in at least two of three matched repetitions. Reports retain
all three values and min/max variability. Windows skipped animation steps and
ESP32 step coverage are reported separately. These are software measurements;
they do not measure GPU/display drops or optical presentation.

Each output directory contains:

- `report.html`: standalone searchable/filterable report with evidence links.
- `report.md`, `summary.json`, `comparisons.json`: findings and completeness audit.
- `measurements.csv`, `step-timings.csv`: durations, coverage and detailed steps.
- `results/`: validated raw Windows JSON and ESP32 JSONL for every observation.
- Frozen manifests, build/source identities, settings, thresholds, repetitions,
  inventories, qualification results and cleanup confirmations.

Reports can be regenerated offline. An incomplete report identifies missing or
invalid cases and must not be presented as a completed comparison. Preserve the
entire directory when archiving or comparing versions. Finish or stop an active
run before invoking Report; the controller lock prevents concurrent report writes.
Reports also summarize ESP32 loop-to-decode and decode-to-submission spans from
the raw step timestamps. The latter includes overlay, drawing and submission.

## Maintainer validation

```powershell
python -m unittest discover -s tests/scripts -p test_current_playback.py
pwsh -NoProfile -File tests/scripts/Test-CurrentPlaybackEntry.ps1
python scripts/esp32/tests/Test-DmdClockTimingFirmware.py
python scripts/esp32/tests/Test-DmdClockSerialFirmware.py
dotnet test DMDClock.sln -c Release
```

These cover selection, frozen references, mismatched files/builds, evidence
validation, cached resume, capture boundaries, allocation/write failures and
cleanup. Physical qualification and the full report remain separate evidence.
No playback correction or release publication is part of this procedure.
